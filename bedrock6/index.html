a self-building software company

bedrock

An agentic, self-modifying environment.

Kubernetes for agents: the agents write, review, ship, and improve the software — and the machinery they run on. A human approves the critical changes and the high-level designs; the rest runs on its own.

↓ scroll
01 / One graph

One graph defines everything — the services, the checks, and the agents themselves.

A running service, a code check, an AI agent — each is the same kind of entry in one build graph, and a single command ships any of them onto the live machine. The agents that write and review the code sit right beside the code they change, so adding a service, a rule, or a new agent is the same motion: edit the graph, ship it. Even the runner that deploys everything is an entry in the graph — so the system upgrades its own machinery the same way it ships a feature. No separate CI server, review bot, or deploy tool to bolt on.

everything is an entity
# a running service
bedrock_service(
    name          = "integrator",
    service_label = "com.bedrock.integrator",
    program       = ":main",
)

# an agent that writes code — declared like the service
agent_spec(
    name    = "implementer",
    prompts = ["//agents/prompts:implementer"],
    harness = "codex",          # the AI backend it runs on
)
02 / Rules as Reflexes

A standard is just an agent wired to an event.

Want every Python change security-audited? Declare an agent — here, one running on a Claude model — and the event it fires on. It wakes on matching changes, reviews them, and votes; mark its approval required, and nothing merges without it. Raising the bar is adding one of these, not building a new system.

  • a reviewer on a code pattern — every Python change gets a security audit
  • a presubmit check on every change — it must pass before merge
  • background agents on idle time — improvement work that never blocks the queue
  • an agent that reads the agents' own logs — the system reviewing itself (§04)
the audit is an agent on an event
# define the agent — a security auditor on a Claude model
agent_spec(
    name    = "fable-auditor",
    prompts = ["//agents/prompts:security-review"],
    model   = "claude-fable-5",
    effort  = "high",
)

# WIRE it to an event — audit every Python change
agent_trigger(
    name    = "security-audit",
    agent   = ":fable-auditor",    # ← rule meets agent
    pattern = "**/*.py",           # matched at run time
    on      = ["added", "modified"],
)
03 / The Loop

It proposes, reviews, and ships — a human approves only what's critical.

One agent writes a change — code, a service, even a new agent. Other agents review it and vote; if they judge it sound, it merges and ships automatically — no human in the loop. A human steps in for two things only: the critical changes — to the deploy machinery, the rules, who's allowed to approve — and the high-level designs that set direction. Once a change ships, the running system updates, including the machinery that produced it; a failed deploy rolls back to the last good version.

nothing merges itself
04 / The Mirror

It turns its own friction into new work.

Every agent action is logged. A second set of agents reads those logs for recurring trouble — repeated failures, missing or stale docs, contradictions — and files each as a ticket. Those tickets re-enter as new work for the build agents and run the same propose-review-gate loop, so a wrong call gets caught, not shipped.

the system reading itself
a meta-process is an agent on a clock
agent_spec(
    name    = "process-auditor",
    prompts = ["//agents/prompts:process-auditor"],
    model   = "claude-fable-5",
    effort  = "high",
)

agent_schedule(
    name  = "process-audit",
    agent = ":process-auditor",
    every = "1h",
)
