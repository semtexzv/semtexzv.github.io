Agents as Stream Processors

2026 · draft~6 min

Distributed agents are hard. Not because any single agent is weak, but because coordinating a fleet of them over a world that keeps changing is a real distributed-systems problem. Here is the shape of it, and the one idea — an append-only log — that makes it tractable.

The whole argument, before the details:

  • Coordinating distributed agents is the hard part — not making any one agent smart.
    • Letting a pool of agents share a repo and message or inject into each other does not hold up: no ordering, races, and no clear notion of who has seen what.
    • A single ultra-smart agent is appealing, but no one agent can attend to everything at once.
    • So disaggregate: many focused agents beat one omniscient agent — a smarter system, not a smarter model.
  • That turns the problem into orchestration: who sees what, who acts when, without stepping on each other.
  • Model every resource as an append-only log. Give each agent offsets into the logs it cares about, and wake it when they advance.
    • An agent does not emit events. It acts on systems — it comments, commits, edits — and those systems append to their own logs.
    • Those appends are what advance other agents' inputs and wake them. The rest of this post is how that works.
  • Bedrock runs exactly this — agents over a monorepo that modifies itself, coordinated through logs — and as a core principle it holds up.

The reference model is stream processing. In Kafka Streams or Flink an operator keeps a little state, reads one or more input logs, applies a function to new records in order, and writes outputs. Treat each agent as an operator and the picture is concrete: three input logs, an agent holding an offset into each, and the systems it writes to.

When those offsets fall behind, the runtime wakes the agent — and the gap becomes the prompt. For the state in the diagram, the delivered message is roughly: 

wake — your registered resources advanced:

  comments  new: f
  documents new: d, e, f
  builds    new: e, f

review what changed and update your work.

The agent reads that and acts: it replies, revises a document, kicks off a job. It never emits an event itself — the systems it touches do, and their appended entries are what wake the next agents.

Use logs, not loose events

The distinction matters. A loose event says that something happened. A log gives you an ordered, append-only sequence and a stable position inside it. The runtime can ask concrete questions: what has this agent seen, what is new since then, and what records must be delivered before the agent is current?

Each resource should expose an append-only changelog. A bug has a comments log. A document has a revisions log. A build has status records. An agent conversation consumes those logs by offset or high-water mark. Processing is then a ratchet: read the next items, update state, act on the systems it owns, and advance the pointer only when the turn has completed.

Track registrations and watermarks

The runtime needs an explicit registration layer. When an agent starts, it has a goal and it declares which resources it cares about: comments on this issue, changes to that document, updates from this build, maybe a queue of tasks created by another agent. That declaration is the subscription set for the conversation.

For every (agent, stream) pair, the runtime stores the agent's high-water mark. It does not matter whether a source system sends a webhook or the runtime polls and compares previous state with current state. Internally the rule is the same: if the stream head is ahead of the agent's mark, the agent is behind.

Wakeup is then mechanical. A new bug comment arrives, a document revision is appended, or a CI result lands. The pointer for that stream has advanced. The runtime finds agents registered on that stream and schedules turns with the delta: "this resource changed; these are the records you have not seen." The agent runs, then acts on the systems it owns — it comments, commits, edits — and finishes. The agent never emits an event itself; the systems it touches append to their own logs, and those appends advance other streams and wake other agents.

Keep causality explicit

This is where the distributed-systems vocabulary is useful. An agent acts inside a causal window: the world up to the watermarks it was given when the turn started. While it runs, the outside world can keep changing. That is fine. The runtime should not pretend the agent saw changes that arrived later; it should deliver them in a later turn.

The main failure mode is self-wakeup. If an agent posts a comment on a bug it is watching, that comment is also an append to one of its input streams. If treated as ordinary new input, the agent can wake itself repeatedly. The runtime needs a clear rule for an agent's own effects.

  • append-after: append the effect, but advance the producing agent's watermark past its own write so it is recorded without becoming a trigger.
  • inject: fold the effect into the running turn's source view, so the agent accounts for it immediately and the later append is just durable history.

Both approaches are workable. The requirement is that self-produced records are causally accounted for and do not create infinite notification loops.

Batch at the right level

When several inputs advance, the runtime has a delivery choice. Edge-triggered delivery wakes the agent for one item or one stream transition at a time. Level-triggered delivery wakes the agent with the current frontier across all changed resources: comments moved to offset 18, the document moved to revision 7, and the build moved to result 42.

For LLM agents, level-triggered wakeups are usually the better default. They give the agent a coherent batch of the current world instead of forcing it through a long sequence of small turns. Edge delivery is still useful where strict per-record ordering is the product requirement.

Spawn agents in infrastructure

Some streams should not wake an existing agent. They should create a new one. A new bug in a bug list might start one implementer conversation keyed by that bug. A new design request might start one design conversation keyed by the request. This should be an infrastructural rule, not an LLM decision.

The rule looks like stream partitioning: for each new record on this stream, start or route to the agent instance for this key. Once created, the agent owns an aspect of the resource. An implementer owns the implementation work. A designer owns the design artifact. A reviewer owns review state. Each one can create more resources, register interest in them, and receive wakeups until its job is done.

Some jobs never fully end. If the resource is long-lived, the owning agent may be long-lived too. It sits at its current frontier and wakes when the resource advances. These are forever agents: ordinary stream processors with durable state and no fixed terminal offset.

deferred: append-only streams need compaction eventually. Old history can be collapsed into the state it implies, but compaction is a separate design problem from the orchestration model.

Where this runs

The practical version is simple: model every resource as a log, let agents register for the logs they care about, store per-agent high-water marks, wake agents when those marks fall behind, and let the systems agents touch append the records that wake the next ones. Orchestration becomes a stream-processing runtime instead of a pile of ad hoc prompts and notifications.

Bedrock is this idea in production. Every resource — issues, designs, reviews, builds, and the agents' own actions — is an append-only log over a single monorepo, and each agent is an operator with offsets into the logs it owns. The twist is that the repo is self-modifying: the agents change the system they run on by acting through the same logs everyone else reads. As a core principle, it holds up.
