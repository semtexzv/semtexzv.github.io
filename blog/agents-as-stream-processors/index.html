Agents as Stream Processors

2026draft~4 min

Stop picturing an agent as a chatbot answering a prompt. Picture it as a node in a topology: it consumes a stream of events, keeps state, and emits new events. The right mental model isn't request/response — it's Kafka Streams.

A chatbot is request/response: a question goes in, an answer comes out, the world resets. That framing falls apart the moment an agent has to run continuously — watching for work, remembering what it already did, reacting to things other agents emit. Request/response has nowhere to put any of that.

Stream processing has had the answer for a decade. In Kafka Streams a program is a topology: source nodes read records off a log, processor nodes transform them, state stores hold the running context, and sink nodes write results back out — usually onto another log that something downstream consumes. Records flow through continuously; the program is the wiring.

Agents map onto that wiring almost one-to-one.

  • a Kafka record → an event: a trigger, a message, a review comment, a webhook
  • a processor node → the agent: read an event, call the model and its tools, decide
  • a state store → the agent's memory: context, scratchpad, what it has already done
  • a sink topic → the agent's actions: a change, a comment, a new task — often re-enqueued as events others consume
  • partitions → isolation: one key (one CL, one conversation) handled in order, independent of the rest

Once you see agents this way, the hard problems stop being prompt problems and start being stream problems: backpressure when the model is the bottleneck; at-least-once vs exactly-once when a tool call has real side effects; keying so related events stay ordered; replay when you want to re-run history against a better model. These are solved problems in stream processing — we get to borrow the solutions.
